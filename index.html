Project Overview

Scalable Web Infrastructure

Traditional web hosting runs on a single server, so a spike in traffic can overload it and take the site down. CloudScale places an Application Load Balancer in front of multiple Amazon EC2 instances, registered in a target group that is health-checked continuously, and uses an Auto Scaling Group to adjust how many instances are running based on average CPU. The stack is deployed in ap-south-1 (Mumbai) across two Availability Zones.

Application Load Balancer

A single public entry point (CloudScale-ALB) that spreads HTTP requests across the fleet.

  • Distributes incoming traffic
  • Health-checks every registered target
  • Routes requests to healthy instances only

Amazon EC2

Ubuntu t3.micro servers running Apache. Every instance serves the identical site.

  • Launched from CloudScale-Launch-Template
  • Spread across two Availability Zones
  • Scales horizontally, never vertically

EC2 Auto Scaling

CloudScale-ASG keeps the fleet at the right size and replaces instances that fail health checks.

  • Minimum 2 · desired 2 · maximum 4
  • Target tracking on 50% average CPU
  • Verified scale-out 2 → 3 and scale-in 3 → 2

Target Group

CloudScale-TG — protocol HTTP on port 80, health check path /.

In this project Holds the registered instances. The ASG registers and deregisters targets automatically.

Amazon CloudWatch

Collects the CPUUtilization metric published by every EC2 instance in the group.

In this project The target tracking policy creates and manages its own CloudWatch alarms on ASGAverageCPUUtilization. No custom dashboards or manual alarms were added.

Amazon VPC

The virtual network containing the load balancer and the instances.

In this project Public subnets in ap-south-1a and ap-south-1b, so the ALB and the ASG both span two Availability Zones.

Security Groups

Stateful virtual firewalls. CloudScale-EC2-SG is attached to every instance in the group.

In this project Allows HTTP to the load balancer, and SSH only from the administrator IP used for setup.

Scope note

This project deliberately stops at compute, networking and load balancing. No database, storage, CDN, DNS or serverless service is part of the deployment — the goal is to demonstrate horizontal scaling and high availability on stateless web servers. The site is served over HTTP at the ALB DNS name; no custom domain or TLS certificate is configured.

Horizontal Scaling

Designed to Scale

Instead of making one server bigger (vertical scaling), CloudScale adds more identical servers (horizontal scaling). CloudScale-ASG tracks average CPU across the group: when it rises above the 50% target, Auto Scaling launches additional t3.micro instances, and when it falls back, the extra instances are terminated. This behaviour was tested on the live deployment — 2 → 3 on load, 3 → 2 on recovery.

      How scaling decisions are made

      CloudWatch metrics → target tracking

      1. Every instance publishes CPUUtilization to CloudWatch at a five-minute interval by default (one minute with detailed monitoring).
      2. CloudWatch aggregates it per Auto Scaling group as ASGAverageCPUUtilization — the average across all InService instances.
      3. The target tracking policy holds that average at 50%. Creating the policy created the CloudWatch alarms behind it automatically; they were not configured by hand.
      4. Above target, the alarm fires and the group launches instances, up to the maximum of 4.
      5. Below target, the low alarm fires and the group terminates instances, down to the minimum of 2.
      Why target tracking

      One number to reason about

      A target tracking policy needs a single setting — the CPU percentage to hold — and AWS works out how many instances that requires. Compared with writing step or simple scaling policies by hand, there are no thresholds, cooldown values or alarm actions to tune, which makes the behaviour easy to explain and easy to reproduce in a demonstration.

      • Metric: ASGAverageCPUUtilization
      • Target value: 50%
      • Capacity bounds: min 2 · desired 2 · max 4
      • Instances added and removed automatically in both directions
      Verified on AWS

      Auto Scaling Demonstration

      The deployed stack was load-tested in ap-south-1. CPU load was generated on the running instances with stress-ng until the group average passed the 50% target, then stopped. Auto Scaling handled both directions on its own. These are observed results from the live deployment, not the browser simulation.

      1. Step 1 · Steady state

        2 healthy instances

        CloudScale-ASG at its desired capacity of 2. Both targets InService and Healthy in CloudScale-TG, one in each Availability Zone.

      2. Step 2 · Load generated

        50%+ average CPU

        stress-ng was run on the instances until ASGAverageCPUUtilization rose above the policy target of 50%.

      3. Step 3 · Scale-out

        2 → 3 instances

        Auto Scaling launched a third t3.micro without any manual action. All three instances reached InService / Healthy and began receiving traffic from the ALB.

      4. Step 4 · Load stopped

        Normal CPU

        The stress test was stopped and the group average fell back below the target value.

      5. Step 5 · Scale-in

        3 → 2 instances

        Auto Scaling terminated the extra instance and returned the group to a desired capacity of 2 — the configured minimum, so it scaled no further.

      How it was built

      Deployment Workflow

      The ten steps used to take this website from a local folder to the running, load-balanced and auto-scaled deployment in ap-south-1.

      1. 01

        Prepare the network

        Public subnets in ap-south-1a and ap-south-1b, with internet access for the instances.

      2. 02

        Create security groups

        One for CloudScale-ALB (HTTP from the internet) and CloudScale-EC2-SG for the instances.

      3. 03

        Launch a base EC2 instance

        Ubuntu t3.micro, then install Apache and copy the site into /var/www/html.

      4. 04

        Create CloudScale-Launch-Template

        Ubuntu AMI, t3.micro, CloudScale-EC2-SG and user data that installs Apache and deploys the site.

      5. 05

        Create CloudScale-TG

        Target type instance, protocol HTTP on port 80, health check path /.

      6. 06

        Create CloudScale-ALB

        Internet-facing, both Availability Zones, HTTP listener on :80 forwarding to CloudScale-TG.

      7. 07

        Create CloudScale-ASG

        Min 2, desired 2, max 4, both AZs, attached to CloudScale-TG with ELB health checks.

      8. 08

        Add the scaling policy

        Target tracking on ASGAverageCPUUtilization with a target value of 50%.

      9. 09

        Test the application

        Open the ALB DNS name and confirm both targets are healthy and serving.

      10. 10

        Test Auto Scaling

        Generate CPU load with stress-ng, observe scale-out 2 → 3, stop the load, observe scale-in 3 → 2.

      Defence in Depth

      Network Security

      Security groups act as virtual firewalls: they control which inbound and outbound traffic is allowed to reach the load balancer and the instances. They are stateful, so a permitted inbound request is automatically allowed to respond. CloudScale-EC2-SG is the group attached to every instance launched by the Auto Scaling group.

      Inbound Rules

      Example rule set

      Example security group inbound rules
      TypePortSourcePurpose
      HTTP800.0.0.0/0Public web traffic reaching CloudScale-ALB
      HTTP80ALB security groupLoad balancer to the instances
      SSH22My IP onlyAdministrative access during setup

      Only these ports are opened. Port 443 is not in use — the site is served over HTTP at the ALB DNS name, so no TLS certificate is configured.

      Practices Applied

      Keeping the surface small

      • CloudScale-EC2-SG accepts port 80 only from the ALB security group, not from the internet.
      • SSH on port 22 is restricted to a single administrator IP address, never 0.0.0.0/0.
      • Unused ports and protocols are left closed by default — security groups deny anything not explicitly allowed.
      • Instances are stateless, so no credentials or application data are stored on them.
      • HTTPS is listed under future enhancements: it needs an ACM certificate and a custom domain, neither of which is part of this project.
